Coupled Regional Rainfall-Induced and Seismic Slope Instability Simulations

Authors: Mirna Kassem & Dimitrios Zekkos
Affiliation: University of California, Berkeley

About

CRISIS is an open-source, python-based model designed to simulate 3D rainfall-triggered and earthquake-triggered landslides at regional scales. It evaluates slope stability across a raster domain, generating realistic 3D landslide geometries — each with a defined location, area, and volume — using a pseudo-3D upslope search algorithm.

CRISIS operates in two modes: a forward predictive analysis that forecasts landslide occurrence over time, and a back-analysis that estimates shear strength parameters from a mapped landslide inventory across a large spatial scale.

The back-analysis mode supports multi-core parallel processing, distributing the search over mapped landslides across available CPU cores to efficiently handle large inventories with hundreds of landslides and dense shear strength search grids.

The model is designed to be highly flexible, accommodating a wide range of user needs — from simple simulations using uniform shear strength and a constant pore pressure coefficient, to advanced configurations with spatially variable 3D strength fields, transient pore pressure files, and coupled seismic displacement models. This makes CRISIS accessible to a broad user base, from practitioners seeking quick regional assessments to researchers conducting detailed process-based studies.

CRISIS accepts spatially and temporally varying pore pressure heads estimated from external transient groundwater flow models, enabling high-resolution, time-evolving stability assessments throughout a storm sequence, or a constant pore pressure ratio \(R_u\) as a simple alternative. For coupled rainfall-earthquake scenarios, seismic displacement is estimated using established empirical models.

2. Overview

CRISIS is a spatially distributed, python-based model for regional landslide hazard assessment. It evaluates slope stability across a raster domain and reconstructs realistic failure geometries using a pseudo-3D approach.

Two triggering scenarios are supported:

  • Rainfall Only — pore-water-pressure driven failures
  • Coupled Rainfall + Earthquake — combined pore-water-pressure and seismic displacement (Forward Analysis only — see below)

Two analysis modes are included:

  • Forward Analysis — predicts landslide occurrence, area, volume, spatial extent, and time of failure (if transient pore pressure files are provided) across a raster domain for a given set of shear strength parameters. Supports both triggering scenarios above.
  • Back-Analysis — given a set of mapped landslides, searches over a user-defined effective cohesion and effective friction angle grid to find the shear strength parameters that best reproduce each observed failure (in terms of location, area, and volume). Rainfall-triggered failures only — the coupled rainfall + earthquake scenario is not available in this mode.

Each analysis can be run in two ways:

  • Interactive GUI — a parameter form for exploratory analysis on a desktop; launched by double-clicking run_crisis.bat (Windows) or run_crisis_macos.command (macOS)
  • Command-line / HPC mode — run directly from a terminal using a JSON configuration file, with no display required

4. Installation

Requirements

  • Python 3.12 or newer — the pinned package versions in requirements.txt (numpy>=2.4.4, rasterio>=1.5.1) have no installable wheels below Python 3.12
  • Internet connection on first run (to download packages)

Windows — GUI

  1. Install Python 3.12+ from python.org. During installation, check "Add Python to PATH".
  2. Double-click run_crisis.bat. On the first run it automatically creates a virtual environment and installs all required packages.
  3. Fill in the parameter form and click Run Model.

⚠ Windows Security Warning: Windows may show a security warning when running run_crisis.bat. This is normal for research software. Click Run to proceed.

To force a full reinstall: run_crisis.bat --reinstall

macOS — GUI

  1. Install Python 3.12+ from python.org (recommended — it bundles Tk/tkinter, which the GUI needs), or via Homebrew: brew install python3 python-tk.
  2. Double-click run_crisis_macos.command. On the first run it automatically creates a virtual environment and installs all required packages.
  3. Fill in the parameter form and click Run Model.

⚠ Error you may see: The first time you double-click run_crisis_macos.command, macOS may show:

"run_crisis_macos.command" Not Opened
Apple could not verify "run_crisis_macos.command" is free of malware that may harm your Mac or compromise your privacy.

Why this happens: Any file downloaded through a browser (Safari, Chrome, etc.) is automatically tagged by macOS as "quarantined," and Gatekeeper blocks unsigned quarantined scripts from running by double-click. This is normal — it does not mean the file is broken or unsafe, only that it wasn't downloaded from the Mac App Store or signed by a registered Apple developer. If the file was also sent to you as a zip created on Windows, it will additionally be missing its "execute" permission (Windows/NTFS has no concept of a Unix execute bit), which causes the same dialog.

How to fix it (do this once per Mac): Open Terminal, then copy-paste the following, replacing <path to this folder> with the actual path to the CRISIS_Code folder (you can drag the folder from Finder onto the Terminal window to auto-fill the path instead of typing it): 

cd "<path to this folder>" && chmod +x run_crisis_macos.command && xattr -d com.apple.quarantine run_crisis_macos.command

After running this once, double-clicking run_crisis_macos.command in Finder will work normally from then on.

⚠ Error you may see: ERROR: [Errno 13] Permission denied while creating crisis_venv_macos, with a path containing Safari.SandboxBroker or TemporaryItems.

Why this happens: Safari auto-unzips downloaded .zip files and lets you open the result directly from its download list/popover. Doing so runs the file from a locked-down temporary sandbox folder instead of its real location on disk — that folder doesn't allow creating new files or directories, which is what fails here.

How to fix it: In Finder, go to wherever you installed it, move the extracted CRISIS_Code (or similarly named) folder to a normal location — Desktop or Documents both work — and double-click run_crisis_macos.command from there instead of from Safari's download popover.

Still running into issues after trying all of the above? As a last resort, run the Windows launcher (run_crisis.bat) instead, inside Windows running on the same Mac via Parallels Desktop, VMware Fusion, or UTM (free), or Boot Camp on older Intel Macs. This avoids every macOS-specific issue described above entirely.

To force a full reinstall: ./run_crisis_macos.command --reinstall (run from Terminal, in the CRISIS_Code folder).

6. Running Without the GUI — Command Line / HPC

Only edit the .json config file — never the .py source files. config_forward_windows.json, config_forward_macos.json, config_back_analysis_windows.json, and config_back_analysis_macos.json (all included in this folder) are ready-to-edit and well documented — each one has a header explaining what the file is and how to run it, plus a comment above every setting explaining what it does. python3 forward_analysis.py config_forward_macos.json

python back_analysis.py config_back_analysis_windows.json

python3 back_analysis.py config_back_analysis_macos.json

from forward_analysis import run_model

7. Input Files

Tip — relative vs. absolute paths: Every path field — in the GUI or in a .json config file — accepts either kind of path.

A relative path (e.g. DEM.h5, ., or ../Example 1/Example 1 Inputs/DEM.h5) is resolved against the current working directory at the time the model runs.

An absolute path (e.g. C:\Users\You\Desktop\CRISIS\Example 1\Example 1 Inputs\DEM.h5 on Windows, or /Users/you/Desktop/CRISIS/Example 1/Example 1 Inputs/DEM.h5 on macOS) always points to the same location no matter what folder you're running from.

What Example 1 and Example 2 use: forward_analysis.py, back_analysis.py, and the GUI live only in CRISIS_Code — the Example 1 and Example 2 folders hold only each example's input data (inside an Example 1 Inputs / Example 2 Inputs subfolder) and outputs, as sibling folders next to CRISIS_Code. So their config files (Example1.json, Example2.json, and the config_forward_*.json / config_back_analysis_*.json templates) use relative paths such as ../Example 1/Example 1 Inputs/DEM.tif and ../Example 2/Example 2 Inputs/DEM.tif. This is just the convention used for these two examples, not a requirement — for your own projects you're free to use absolute paths instead, or to keep your input files in the same folder as the config file (in which case the path fields would just be filenames, or . for a directory).

HDF5 Raster Format

Whenever you have a raster — a 2D spatial grid (rows × cols) such as the DEM, PGA, or PGV, or a 3D array (rows × cols × depth layers) such as cohesion or friction angle — it must be saved as an HDF5 file (.h5) containing a single dataset stored under the key /data. Here, /data is the internal HDF5 dataset name (the label used to locate the array inside the file); your NumPy or MATLAB matrix can be named anything. Note that slope, flow direction, and flow accumulation are not file inputs — CRISIS computes them automatically from the DEM (see below).

Exception — the DEM can also be a GeoTIFF: dem_file is the one raster input that doesn't have to be HDF5 — a GeoTIFF (.tif/.tiff) works too, and lets CRISIS read Cell_size/xmin/ymin directly from the file instead of requiring them to be typed in by hand. PGA, PGV, cohesion/friction angle 3D arrays, pore pressure, and volumetric water content files must still be HDF5. See the Topography subsection below for details.

Why HDF5? HDF5 is a binary, compressed storage format, which makes it far more efficient than plain-text raster formats — files are smaller on disk, and reading/writing them is substantially faster, especially for the large 3D arrays (rows × cols × depth layers) used for cohesion, friction angle, pore pressure, and volumetric water content across many time steps. This efficiency is why CRISIS standardizes on HDF5 for all raster inputs and outputs.

If your rasters are currently saved as ASCII files (e.g. Esri ASCII grids with a header block of ncols, nrows, xllcorner, yllcorner, cellsize, NODATA_value), read them into MATLAB or Python as a raster matrix — without the header — and then write that matrix into an HDF5 file using the Write examples below.

Python — Read ASCII raster (header skipped)

import numpy as np

# skip the 6-line Esri ASCII header, keep only the numeric grid
matrix = np.loadtxt('File.asc', skiprows=6)

MATLAB — Read ASCII raster (header skipped)

% arcgridread() reads an Esri ASCII grid and returns the matrix without its header
matrix = arcgridread('File.asc');

Python — Write (2D or 3D raster matrix → HDF5)

import numpy as np
import h5py

# matrix is your 2D (rows × cols) or 3D (rows × cols × depth) NumPy array
with h5py.File('File.h5', 'w') as f:
    f.create_dataset('data', data=matrix)   # 'data' is the dataset key inside the file

Python — Read

import h5py

with h5py.File('File.h5', 'r') as f:
    matrix = f['data'][:]   # reads the dataset stored under the key 'data'

MATLAB — Write (2D or 3D raster matrix → HDF5)

filename = 'File.h5';
% matrix is your 2D or 3D MATLAB array
h5create(filename, '/data', size(matrix));   % '/data' is the dataset key inside the file
h5write(filename, '/data', matrix);

MATLAB — Read

matrix = h5read('File.h5', '/data');   % reads the dataset stored under the key '/data'

Note: MATLAB and Python may interpret multi-dimensional HDF5 arrays differently. To avoid inconsistencies, use Python consistently for HDF5 handling.

Topography — the only raster file required to define the domain

CRISIS only requires a single raster file to define the model domain: the Digital Elevation Model. Slope, flow direction, flow accumulation, and the x/y coordinate grids are computed automatically from the DEM.

File / ParameterDescription
dem_fileHDF5 (.h5) or GeoTIFF (.tif/.tiff) file — digital elevation model (meters)
Cell_sizeDEM grid resolution (meters)
xminEasting of the center of the lower-left DEM cell (meters) — the left edge of the domain
yminNorthing of the center of the lower-left DEM cell (meters) — the bottom edge of the domain

Together, dem_file, Cell_size, xmin, and ymin fully define the raster grid — every other topographic array used by the model is derived from them internally.

GeoTIFF DEM — Cell_size/xmin/ymin are auto-derived, not typed in: If dem_file is a GeoTIFF, CRISIS reads Cell_size, xmin, and ymin directly from the file's embedded geotransform — any values entered in those three fields (in the GUI or a config file) are silently overridden and have no effect. This only applies to GeoTIFF; for an HDF5 DEM, which carries no georeferencing, all three must still be entered manually as before.

The GeoTIFF must be in a projected CRS in meters (see the CRS note below — the same projected-vs-geographic requirement applies to a GeoTIFF's own embedded CRS, not just the model's Coordinate_Reference_System setting) and have square, non-rotated pixels. CRISIS validates all of this when the file is read and raises a clear error — naming the actual problem and, for a geographic CRS, how to reproject it in QGIS or ArcGIS Pro — rather than silently producing wrong results.

Note: xmin and ymin must always be in meters, regardless of which Coordinate_Reference_System you select — the same requirement applies to Cell_size. This is because slope, landslide area, and landslide volume are all computed directly from Cell_size (e.g. area = Cell_size²), so it must be a real linear distance for those results to be correct, and xmin/ymin must stay in that same unit since they are used together to build the model's coordinate grid.

This is also why Coordinate_Reference_System must be a projected CRS, not a geographic one. A geographic CRS (e.g. WGS 84, NAD 83) locates points as longitude/latitude angles in degrees, with no fixed real-world distance per unit. A projected CRS (e.g. any UTM zone, State Plane, Albers) flattens the earth onto a plane and locates points as a linear easting/northing distance — normally in meters — from a fixed origin, so its units are directly compatible with meter-based xmin/ymin/Cell_size. Selecting a geographic CRS would tag the output shapefiles with degree-based units while their actual coordinates remain meter-scale numbers, making them unusable in GIS software. For this reason, the GUI's Coordinate_Reference_System dropdown only lists projected systems, and selecting or typing in a geographic one is blocked with a validation error before the model runs.

How Slope, Flow Direction, and Flow Accumulation Are Computed by CRISIS

These are computed by a Python re-implementation of MATLAB TopoToolbox (Schwanghart & Scherler, 2014):

  • Slope — the steepest 8-connected downhill gradient at each cell, equivalent to TopoToolbox's GRIDobj/gradient8.m
  • Flow Direction — D8 steepest-descent routing (E=1, SE=2, S=4, SW=8, W=16, NW=32, N=64, NE=128), after filling depressions and resolving flat areas toward their outlet, equivalent to TopoToolbox's FLOWobj(DEM,'preprocess','fill')
  • Flow Accumulation — upstream contributing cell count, propagated along the flow-direction network, equivalent to TopoToolbox's flowacc(FD); converted internally to a contributing area in m² by multiplying by Cell_size2

Flow Direction and Flow Accumulation take roughly a minute to compute on a large DEM. In the GUI, the Topography tab's preview panel computes them once and caches the result, so the same DEM and Cell Size are not recomputed a second time when the model is actually run.

D8 flow direction, determined from the steepest downhill neighbor of each cell, and flow accumulation, the number of upstream cells draining into each cell — both computed automatically from the DEM (modified from Esri, 2014).

Seismic Rasters (Coupled mode only)

These files are required only when Triggering_Indicator = 2 (Coupled Rainfall + Earthquake mode). When Triggering_Indicator = 1 (Rainfall only), this section can be ignored and the corresponding fields left blank.

FileDescription
PGA.h5Peak ground acceleration (g)
PGV.h5Peak ground velocity (cm/s) — required only for the Bray & Macedo displacement model or the Rathje PGAV variant

Pore Pressure Files (variable pore pressure option only)

The hydrological model is controlled by Hydrological_model_indicator: set to 0 for a spatially uniform, time-constant pore pressure ratio \(R_u\) (no files needed), or set to 1 to load spatially and temporally varying pore pressure head files. The files below are required only when Hydrological_model_indicator = 1.

One file per time step and depth layer, named exactly: Pressure_head_T{time_index}Z{depth_index}.h5

Example: Pressure_head_T3Z2.h5 = time step 3, depth layer 2. The time index T is 0-based and runs from 0 to time_points − 1. The depth index Z is 1-based and runs from 1 to Depth_points, where Z1 corresponds to the shallowest depth layer (z_min, nearest to the surface) and higher indices correspond to deeper layers.

These files are produced by an external transient groundwater flow model. Examples of commonly used models include ParFlow, TRIGRS, MODFLOW, etc.

Volumetric Water Content Files (variable water content option only)

The effective stress formulation is controlled by Strength_variation_with_theta: set to 0 to assume full saturation everywhere (Bishop's \(\chi = 1\), no files needed), or set to 1 to compute \(\chi\) from spatially and temporally varying volumetric water content files. The files below are required only when Strength_variation_with_theta = 1.

Note: When Hydrological_model_indicator = 0 (constant \(R_u\) option), Bishop's effective stress coefficient is automatically set to \(\chi = 1\) everywhere, and no volumetric water content files are required — Strength_variation_with_theta is ignored in this case.

One file per time step and depth layer, named exactly: Theta_T{time_index}Z{depth_index}.h5

Each file is a 2D raster of volumetric water content at that time step and depth layer.

Example: Theta_T3Z2.h5 = time step 3, depth layer 2. The time index T is 0-based and runs from 0 to time_points − 1. The depth index Z is 1-based and runs from 1 to Depth_points, where Z1 corresponds to the shallowest depth layer (z_min, nearest to the surface) and higher indices correspond to deeper layers.

Like the pore pressure head files above, these are produced by the same external transient groundwater flow model (e.g. ParFlow, TRIGRS, MODFLOW, etc.).

These files are used to compute Bishop's effective stress coefficient \(\chi\), which scales shear strength based on the degree of saturation at each grid cell, depth, and time step:

\[ \chi = \frac{\theta(x,y,z,t) - \theta_r}{\theta_s - \theta_r} \qquad (1) \]

where \(\theta(x,y,z,t)\) is the volumetric water content at a given grid cell, depth, and time instant, computed by the groundwater flow model; \(\theta_s\) is the saturated volumetric water content; and \(\theta_r\) is the residual volumetric water content. The result is clipped to the range [0, 1].

3D Shear Strength Files (spatially variable strength option only)

Shear strength is controlled by Strength_status: set to 0 for spatially uniform effective cohesion \(c'\) and effective friction angle \(\varphi'\) applied to all cells and depths (scalar values, no files needed), or set to 1 to load spatially varying 3D arrays of \(c'\) and \(\varphi'\). The files below are required only when Strength_status = 1.

FileDescription
cohesion_3d.h5Effective cohesion \(c'\) (kPa) — shape (rows, cols, Depth_points)
phi_3d.h5Effective friction angle \(\varphi'\) (degrees) — shape (rows, cols, Depth_points)

Mapped Landslide Files (back-analysis only)

FileDescription
ID.xlsxSingle column of mapped landslide IDs, no header
LD{ID}.xlsxOne file per mapped landslide: a header row followed by one data row, with columns in this order — Mapped Area (m²), Mapped Centroid X (m), Mapped Centroid Y (m), Mapped Volume (m³)

Note: CRISIS reads LD{ID}.xlsx by column position, not by the header text — column order is what matters, not the exact wording of row 1 (the names above are just the recommended convention for readability). A header row must still be present, though — row 1 is always skipped, so if it's missing, the first data row is read as the header instead and the actual data is lost.

Mapped Centroid X/Y can be extracted directly from your mapped landslide polygons in GIS software — e.g. the Centroid tool in QGIS or ArcGIS Pro — as long as the polygons are in the same projected coordinate system used elsewhere in the model (see the Coordinate_Reference_System note earlier in this document). Exporting the polygon layer's attribute table after adding centroid X/Y fields gives you these values directly.

Refer to the Example 2 Inputs folder (inside Example 2) to see a sample of these files.

Note: A "time step" has no fixed real-world duration in CRISIS itself — it can represent an hour, 30 minutes, a day, or any other interval. That duration does not enter the slope stability calculations at all; it is defined entirely by the external hydrological model that produced your pore pressure head files (Pressure_head_T{t}Z{d}.h5) and volumetric water content files (Theta_T{t}Z{d}.h5), whose temporal spacing is whatever you set it to when generating them. CRISIS simply processes them in index order as t = 0, 1, ..., time_points − 1.

Because CRISIS itself has no concept of what each time step corresponds to in real time, you need to keep track of that mapping yourself (e.g. "each time step = 1 hour") in order to correctly interpret outputs that are indexed by time step — Earthquake_time_point, the Landslide Area Density plot, Total_landslides_with_time.xlsx, and the per-time-step columns in Individual_landslides_with_time.xlsx.

Tab 6 — Hydrological Formulations

ParameterDescription
Hydrological_model_indicator0 = Geospatially and temporally uniform pore pressure coefficient \(R_u\) · 1 = Geospatially and temporally variable pore pressure heads from files
RuPore pressure ratio, from 0 (dry) up to \(R_{u,max}\) — see below (Constant \(R_u\) option only)

The pore pressure coefficient is defined as:

\[ R_u = \frac{u}{\gamma\, z} = \frac{\psi\, \gamma_w}{\gamma\, z} \qquad (2) \]

where \(u\) is the pore pressure (stress); \(\gamma\) and \(\gamma_w\) are the respective saturated material and water unit weights; \(z\) is the vertical depth (m); and \(\psi\) is the pressure head (m).

Note: \(R_u\) does not range from 0 to 1 — it ranges from 0 (dry, \(\psi = 0\)) up to \(R_{u,max}\), which corresponds to fully saturated conditions, i.e. pressure head equal to depth (\(\psi = z\)). Substituting \(\psi = z\) into the definition above (Eq. 2) gives: \[ R_{u,max} = \frac{\gamma_w}{\gamma} \qquad (3) \] Since \(\gamma\) (soil) is always greater than \(\gamma_w\) (water, 9.81 kN/m³), \(R_{u,max}\) is always less than 1 — e.g. for \(\gamma = 22\) kN/m³, \(R_{u,max} \approx 0.446\). Entering an Ru value above the true \(R_{u,max}\) for your soil's unit weight corresponds to a pore pressure head greater than the depth itself, which is not physically achievable.

Note: Even with a constant \(R_u\) (no pore pressure files), you still need to discretize the subsurface via z_min, z_max, and Depth_points (Tab 5 — Scalar Inputs) — a constant \(R_u\) does not remove the need for depth layers. From the definition above (Eq. 2), the pressure head at depth \(z\) works out to: \[ \psi(z) = \frac{R_u\, \gamma\, z}{\gamma_w} \qquad (4) \] so \(R_u\) acts as a constant slope describing how pressure head grows with depth. If you evaluate only a single depth (Depth_points = 1, or z_min = z_max), every triggering cell fails at exactly that one depth, with no depth variation at all. Define z_min/z_max to span the subsurface thickness you actually want to search, then set Depth_points high enough to resolve that range into distinct candidate failure surfaces — the same way you would with variable pore pressure files.

Also keep in mind what constant \(R_u\) does not give you: because \(\psi(z)\) above depends only on \(z\), every cell at a given depth has exactly the same pressure head at every location and every time step — a constant \(R_u\) has no spatial variability and does not evolve over the simulation. Only the variable pore pressure file option (Hydrological_model_indicator = 1) captures pressure heads that vary in space and time.

10. Model Physics

Forward Analysis — Rainfall

The factor of safety \(F_s\) is computed at every raster cell, depth layer, and time step:

\[ F_s = \frac{\tan\varphi'}{\tan\beta} + \frac{c' - \chi\,\psi\, \gamma_w \tan\varphi'}{\gamma\, z \sin\beta \cos\beta} \qquad (5) \]

where:

  • \(c'\) — effective cohesion (kPa)
  • \(\varphi'\) — effective friction angle (degrees)
  • \(\gamma\) — unit weight of soil (kN/m³)
  • \(\gamma_w\) — unit weight of water (kN/m³)
  • \(z\) — vertical depth (m)
  • \(\beta\) — slope angle (degrees)
  • \(\psi\) — pressure head (m)
  • \(\chi\) — Bishop's effective stress coefficient (Eq. 1): \(\chi = (\theta - \theta_r)/(\theta_s - \theta_r)\), clipped to the range [0, 1]. Set to 1 everywhere when Strength_variation_with_theta = 0 (full saturation assumed).

The pressure head \(\psi\) is computed in one of two ways:

  • Constant \(R_u\) — \(\psi\) is derived from the user-supplied pore pressure coefficient (Eq. 4): \(\psi(z) = \dfrac{R_u\, \gamma\, z}{\gamma_w}\)
  • Variable pore pressure files — \(\psi\) varies spatially and over time, read from external HDF5 files named Pressure_head_T{t}Z{d}.h5 (e.g. Pressure_head_T0Z1.h5), computed by an external groundwater flow model

A cell is classified as a triggering cell when \(F_s < 1.0\).

Infinite slope stability limit equilibrium method (U is the pore water force, N is the normal force, W is the weight of the block, T is the resistive shear force acting at the base of the block, and L is the block length in translation).

Forward Analysis — Seismic Displacement (Coupled mode)

At and after the earthquake time step, each cell is checked for failure from rainfall, seismic displacement, or both. For seismic failure, the model computes a yield acceleration from the factor of safety (Eq. 5) and estimates the Newmark displacement using one of four empirical models as implemented in the RESTAB model (Gong et al., 2023)

ModelReference
JibsonJibson (2007)
Rathje RigidRathje et al. (2014)
Rathje FlexibleRathje & Antonakos (2011)
Bray & MacedoBray & Macedo (2019)

A cell is classified as seismically unstable when the computed displacement exceeds the user-specified threshold (typically 5 cm).

Pseudo-3D Landslide Geometry

An upslope geomorphic projection algorithm is used to expand the 1D triggering cell at the triggering depth to a realistic 3D landslide polygon. The algorithm uses an upslope search algorithm along the D8 flow network, constrained by a flow accumulation raster. The result is a realistic 3D landslide polygon with a defined location, area, and volume that follows the natural drainage structure of the terrain.

Identification of upslope cells for a target cell from its eight neighboring cells using flow direction information.

Schematic of the pseudo-3D landslide formation methodology, starting at a triggering cell and expanding upslope to define the landslide geometry.

The depth of each extended cell is computed as:

\[ Z_E = H_E - \left[ D \cdot \tan(\beta_T) + (H_T - Z_T) \right] \qquad (6) \]

where \(H_E\) is the elevation of the extended cell; \(D\) is the Euclidean distance between the triggering and each extended cell; and \(\beta_T\), \(H_T\), and \(Z_T\) are the slope inclination, elevation, and triggering depth of the triggering cell, respectively (Gong et al., 2023).

In the pseudo-3D procedure, the failure surface initially has a constant slope inclination equal to the slope inclination at the triggering cell. The model then adjusts the slope inclination at each extended cell, such that the slope of the failure plane becomes steeper as the distance from the triggering cell increases. This is achieved by first identifying the extended cell with the highest elevation and the minimum distance between this cell and the triggering cell (\(Min\_dist\)). The model then computes the inclination angle \(M_{slope}\) (in degrees, rounded up to the next whole degree) of the line connecting this cell (at the surface) with the triggering cell at its triggering depth. Subsequently, the rate of change in slope, \(dx_{slope}\), is determined:

\[ M_{slope} = \left\lceil \arctan\!\left(\frac{\max(\text{Elevation of all landslide cells}) - (H_T - Z_T)}{Min\_dist}\right) \right\rceil \qquad (7) \]


\[ dx_{slope} = \frac{M_{slope} - \beta_T}{Min\_dist} \qquad (8) \]

The failure depth at every extended cell is then recomputed using this distance-dependent slope, replacing \(\beta_T\) in the \(Z_E\) equation above (Eq. 6) with a linearly steepening angle:

\[ H_F(D) = H_T - Z_T + D \cdot \tan\!\big(\beta_T + D \cdot dx_{slope}\big) \qquad (9) \]

where \(H_F(D)\) is the elevation of the refined failure plane at distance \(D\) from the triggering cell; the final failure depth at each extended cell is \(H_E - H_F(D)\), and only cells where this is still positive remain part of the landslide.

Schematic of the failure surface geometry: (a) initial surface with constant slope equal to that of the triggering cell; and (b) adjusted failure plane with slope increasing with distance from the triggering cell.

Back-Analysis — Shear Strength Estimation

For each mapped landslide and each \((c', \varphi')\) combination on the search grid, the model is run over the local raster sub-domain. The combination that minimises a combined error between the modeled and observed landslide location, area, and volume is selected as the back-calculated shear strength. Results across all landslides are summarized and fitted with a Mohr-Coulomb failure envelope (mean ± statistical bounds) using linear regression.
